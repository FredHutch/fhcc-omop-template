# ETL Key Decisions
Summarized below are key decisions in our OMOP ETL implementation within Databricks:
- **Bundles** - We have utilized Declarative Automation Bundles to define the jobs for updating OMOP tables and running data checks on a regular basis. This infrastructure-as-code (IaC) approach which defines and manages out jobs, variables, and alerts through YAML for version control and transparency. It has also supported our continuous integration and deployment (CI/CD) process, allowing for automated updated of jobs as pull requests are merged.
- **ID Generation** - After consideration of several potential methods for generating unique ID values (e.g., hash, row_number, GENERATED ALWAYS AS IDENTITY, ID mapping table), we utilized a hash function (xxhash64). This deterministic ID generation method will maintain consistency in the IDs between weekly fully table refreshes, a need from our users. While this hash function may result in non-uniqueness in large data sets, we have automated checks monitoring for this and have not encountered this in our data yet. This does return a BIGINT, which is not in line with the standard for this column to be an INT, but due to limited options for ID generation within the INT data type and knowledge that our direct collaborators are using systems that accept a BIGINT we decided to use this BIGINT VALUE.
- **Data Quality** - As a complement to DQD for data quality monitoring, we have utilized the DQX, a data quality framework for Apache Spark with a Python library that enables us to define, monitor, and address data quality issues. This is set up to run every time our OMOP tables are updated. It runs binary (pass/fail) checks on individual records to identify records, with “error” and “warning” level checks defined through a YAML. Impact records can be quarantined and excluded from the final tables if desired.
- **Weekly Full Table Update** - We considered incremental updates of our tables, but due to negligible performance benefits and added code complexity we have implemented full table refresh. These run on a weekly basis to allow our users to have reasonable up to date data in line with common needs.
- **Table Refresh** - We considered different options to reduce potential downtown of data if issues occur during the process of full weekly table updates. After successfully executing the logic to determine the updated table within a temporary table, we update the final table accessible to users through an “INSERT OVERWRITE” statement. Since table are updated through a combination of sequential and parallel tasks, an error may result in only a subset of table being updated, but with ID Generation method detailed above the IDs will still be consistent and this will not cause major data issues during the short period it takes for our team to address the error.
